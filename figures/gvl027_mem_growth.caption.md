**Supplementary Figure X. Resident memory usage of the GenVarLoader v0.27.0 data loader during data loading, as a function of sequence length, dataset, and output type.**

Each panel shows one requested output sequence length (2, 16, 128, or 1,024 kb). Within each panel, each line is one data-loading run on a single node (cn-03, 32 threads, 96 GiB memory requested, shown by the red dotted line). Color indicates the dataset: 1000 Genomes Project genotypes (1kGP, blue) and TCGA-ATAC (orange). Line style indicates the output type: personalized haplotype sequences (solid) or base-pair-resolution coverage tracks (dashed). 1kGP provides only haplotypes; TCGA-ATAC provides both. All runs used the eager loader (mode=none), in which every mini-batch is decoded from disk on demand, so the curves reflect the memory cost of producing batches rather than of reusing pre-decoded data. Batch size was scaled inversely with sequence length to hold the number of base pairs per batch approximately constant.

Axes. The y-axis is resident set size (RSS), the physical RAM held by the loader process, in GiB. The x-axis is the cumulative number of instances decoded (millions), where one instance is a (region, sample) pair. We plot RSS against instances decoded rather than wall-clock time because all runs were given the same 180 s budget, and the number of instances produced within that budget differs by orders of magnitude across sequence lengths (a 1,024 kb instance contains 512 times more sequence than a 2 kb instance and takes correspondingly longer to decode). Plotting against instances decoded normalizes for this difference and shows how far each run progressed as the horizontal extent of its curve.

Memory model. GVL does not materialize whole personalized genomes. The reference genome is loaded once into RAM (approximately 3 GiB for GRCh38) and contributes a fixed baseline that is independent of sequence length. The genotype store and the coverage-track intervals are instead memory-mapped: the operating system exposes each file as addressable memory but loads a given region into RAM only when it is first accessed, and may evict it again later. Two quantities therefore determine RSS: (i) the working set, the amount of memory-mapped genotype or track data that has been accessed and remains resident, and (ii) the decoded batch, the dense output array assembled for the current mini-batch, whose size equals (instances per batch) × (sequence length) × (bytes per base pair) and which is allocated and freed on each iteration. Different datasets and output types load these two quantities differently, which accounts for the qualitatively different curves.

1kGP haplotypes are working-set-limited. 1kGP contains approximately 7.7 million instances backed by a large genotype store, and RSS is dominated by quantity (i). At 2 to 128 kb, decoding is fast enough that the loader traverses the full dataset one or more times within 180 s, the genotype store becomes fully resident, and RSS plateaus near 115 GiB. At 1,024 kb, each instance is more expensive to decode, the loader completes only about 13% of a single pass (note the shorter blue curve), a correspondingly smaller fraction of the genotype store is accessed, and peak RSS is lower (approximately 54 GiB). The largest sequence length therefore uses less memory not because long sequences are intrinsically cheaper, but because the fixed time budget accesses less of the data. The UKBB dataset, which is also genotype-only and produces haplotypes but contains far more instances, occupies this same working-set-limited regime and is omitted from the figure as redundant. It would differ from 1kGP only in the larger absolute size of its genotype store and the correspondingly smaller fraction of it accessed within the time budget.

TCGA-ATAC is batch-size-limited. TCGA-ATAC contains approximately 147,000 instances, so the loader completes many full passes at every sequence length and coverage is never limiting; RSS is instead dominated by quantity (ii). At short sequence lengths the batch size is capped by the dataset size (a batch cannot exceed approximately 147,000 instances), so the decoded batch grows in proportion to sequence length and peak RSS rises accordingly (haplotypes: 6 GiB at 2 kb, 13 GiB at 16 kb). Once the sequence length is large enough that the configured batch size falls below the dataset size, holding base pairs per batch constant fixes the decoded batch size, and peak RSS for haplotypes saturates (approximately 36 GiB at both 128 and 1,024 kb). Coverage tracks reach higher RSS than haplotypes for two reasons: each track base pair is stored as a 4-byte value versus approximately 2 bytes for a diploid haplotype base, and the resident track working set continues to grow with sequence length because longer windows access more of the genome-wide track data (approximately 74 GiB at 128 kb, 111 GiB at 1,024 kb), whereas the sparse genotype working set saturates.

Additional features. The rapid oscillation on each plateau reflects the repeated allocation and release of the decoded batch on each iteration, not disk swapping. Peak RSS exceeds the 96 GiB request in several configurations (1kGP haplotypes at 2 to 128 kb, and TCGA-ATAC tracks at 1,024 kb). This is possible without job failure because most of the resident memory in these cases is memory-mapped file data, which the operating system can reclaim on demand; the decoded batch, in contrast, is non-reclaimable. RSS drops to approximately 4 GiB at the end of every run once the loop terminates and the final batch is released, returning the process to its baseline footprint.
